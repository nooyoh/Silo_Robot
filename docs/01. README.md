작품명(대외 명칭)도 "사일로봇"으로 통일 — 팀명을 그대로 작품명으로 사용 ([[02. 결정로그]]).
자력으로 철제 벽면에 부착해 이동하는 **궤도형 벽등반 로봇**. 2025년에는 청소 기능을 얹어
청소 로봇으로, 2026년에는 카메라 비전 기반 결함 탐지 기능을 얹어 점검 로봇으로 공모전에
출품했다. 두 해에 걸쳐 주제가 바뀌었음에도 등반 몸체 자체는 크게 바뀌지 않았다는 관찰에서,
몸체를 공용 플랫폼으로 두고 기능부를 교체 가능한 모듈로 설계하면 활용처를 넓힐 수 있다는
방향성을 갖고 있다 — **단, 이 모듈화는 아직 아이디어 단계이며 실제 탈부착 구조나 교체
이력은 없다.** ([[02. 결정로그]] 참조)

### 시스템 개요
- 이동 방식: 궤도(무한궤도)형 — 휠형·다리형 대비 벽면 접촉 면적이 넓어 부착 안정성이 높다고
  판단해 채택 ([[02. 결정로그]], 2025년 시작 시점부터 결정)
- 벽면 부착 방식: 자력 (철제 구조물 대상). 처음부터 자력으로 시작해 흡착 등 다른 방식은
  비교 검토하지 않음
- 자력 조절 방식: 2026년 할바흐 배열(간섭용 자석 1열, 수직 이동)로 변경. 2025년에는 영구자석
  회전식이었으나 회전 공간 필요·거리에 따른 간섭 효율 저하 문제로 폐기 ([[02. 결정로그]])
- 궤도 구조: 2026년 스프링 쇼바(서스펜션) 추가로 곡률 적응형 구조 도입. 2025년에는 궤도가
  몸체에 고정 부착되어 곡면 대응 불가 ([[02. 결정로그]])
- 2025년 기능: 청소
- 2026년 기능: 카메라 비전 기반 결함 탐지 — 벽면 근접 이동이 가능한 구조적 특성상 드론 등
  원거리 관측 대비 정밀 탐지에 강점이 있다고 판단해 청소에서 전환 ([[02. 결정로그]])
- 대상: 2026년(해운물류)은 항만 시설 내 철제 탱크 사일로로 한정. 한이음으로 넘어오며 "자력이
  붙을 수 있는 철제 구조물 전반"으로 적용 범위 확장 (대상 면 조건은 "자력이 통하는 철" 정도로만
  현재 정의됨 — 상세 미확정)
- 현장 문제의식: 밀폐공간(탱크·사일로 내부) 점검·청소 작업은 질식·유해가스·추락 등의 위험이
  크다는 것이 로봇 도입의 배경이다. 국내 조선업 밀폐공간 질식재해 통계와 공식 안전보건 자료의
  출처는 [[5. 보고서/04. 보고서 통계·출처 검증]]에 정리했다.

### 컴퓨팅 구조
- **STM32** (**최종 탑재 NUCLEO-F401RE**, 2026-08-21 실물 Device ID `0x433` 확인. 펌웨어는
  F411RE도 빌드 가능): 모터 드라이버 2개 실시간 제어, 베어메탈
- **Jetson Nano B01** (로봇 탑재): STM32와 통신, 모터 제어 외 로봇 측 두뇌 역할 전반
- **Jetson Orin Nano Super** (서버): Nano B01의 실시간 영상처리 성능 부족으로 영상 처리만 분리
  수신 — 결함탐지 등 비전 처리 + 그 외 서버 역할 전반 ([[02. 결정로그]])
- **라즈베리파이4 + 7인치 터치스크린**: 대시보드 — 원격 모니터링 + 터치스크린 로봇 제어.
  로봇과 분리된 휴대용 콘솔, C++/Qt6 네이티브 앱
- 상세: [[3. 소프트웨어/01. STM32]] · [[3. 소프트웨어/02. 젯슨]] · [[3. 소프트웨어/03. 대시보드]]

### 소프트웨어 설계와 구현 상태
- STM32: CubeIDE + HAL, 베어메탈. PWM 4채널(드라이버 2개×2채널), 엔코더는 좌/우 앞쪽 모터만,
  거리센서 3점 ADC. 정지는 별도 명령+래치, 통신 끊김 시 자체 타임아웃 페일세이프
- Nano B01: ROS2 Eloquent + Python(rclpy), 기능별 노드 분리. IMU 직결, 카메라는 CSI +
  `nvarguscamerasrc`
- 통신 구조: STM32 ↔ Nano B01 = ST-LINK VCP UART 양방향(하행 6바이트 제어 / 상행 8바이트
  텔레메트리, 각 20Hz) / Nano B01 → Orin = RTSP 720p30 / Orin·Nano B01 → 대시보드 =
  WebSocket(대시보드가 서버), 전 구간 Tailscale
- 결함탐지: YOLO 계열 모델을 균열 데이터로 학습하고 Orin에서 TensorRT 추론하는 파이프라인을
  구현 중이다. Google Colab Pro를 학습용으로 구매했으나 실제 학습 완료·Orin 실추론·정량 성능은
  아직 검증되지 않았다. 탐지 결과는 Qt 영상 오버레이와 기록으로 연결하는 구조다.
- 이동 명령 값 범위: throttle/turn 각각 -100~100 정수, 전 구간 동일

### 2025년 실패와 2026년 개선
- 2025년 궤도 전파손 사고: 공차 미고려 + 3D 프린팅 적층 방향과 하중 방향 불일치로 첫 구동 시
  궤도 전체 파손. 임베디드 지식 부족으로 소프트웨어도 단순 접근에 그침. ([[03. 트러블슈팅]])
- 2026년 개선: 팀이 4학년이 되며 습득한 전문지식으로 궤도 재설계(곡률 적응형), 팀원 각자
  임베디드 부트캠프 수강으로 지식 보강

### 2026-08-18 통합 검증
- **관제 콘솔(RPi4) → Nano B01 → STM32 → 모터 4개**의 제어 경로를 실제로 검증했다. 처음에는
  STM32 부팅 정지 래치와 Nano 브릿지의 초기 상태가 어긋났지만, 대시보드에서 비상정지를 한 번
  설정·해제하면 정상 구동됨을 확인했고 해당 브릿지 버그도 수정했다.
- Nano B01 CSI 카메라 영상은 RTSP로 RPi4 관제 콘솔에 실시간 송출되는 것을 확인했다.
- 2026-08-24 궤도·프레임과 모터 4개의 기구 조립은 완료했다. 단, 전장 탑재·최종 배선,
  조립 상태의 부하 주행, 벽면 등반, Orin 실추론은 별도 검증이 남아 있다.

### 2026-08-24 기구 조립 상태
- 좌우 궤도, 모터 4개와 프레임의 **기구 조립을 완료**했다. 사진으로 형상을 확인했으며,
  전장용 아크릴판·Nano B01·STM32·모터드라이버의 탑재와 최종 배선은 남아 있다.
- 보고서와 영상에는 `궤도·프레임 기구 조립 완료`로 적는다. 전장·자석·센서까지 포함한
  `최종 로봇 완성`, 부하 주행과 벽면 등반 성공은 실제 시험 전까지 사용하지 않는다.

### 2026-08-24 최신 코드 상태
- 엔코더·조향·좌표계 정합, 차선 간격, stale/무진행 정지, 배터리 `BE`·저전압 래치,
  안전 사건 기록과 Orin 잔상 제거를 반영했다.
- 실제 STM32 C를 포함한 장치 외 검증 63개와 Nano 패키지 계약 4개가 통과했다.
- 거리센서가 미연결이어도 8개 노드 부팅은 되도록 `require_distance:=false`를 유지하되,
  일반 부팅의 자율주행은 `armed=false` 게이트가 막는다. 시연/HIL은 명시적 `demo-drive` 사용
  (`bench-autonomy`는 호환 별칭).
- STM32 모터 제어선을 좌·우 블록으로 재배치했다. 정확한 핀은 [[2. 하드웨어/05. 배선도]]만 사용한다.
  Nano↔STM32는 짧은 ST-LINK USB 한 가닥을 유지한다. 새 핀맵의 F401/F411/배터리활성 ARM 빌드와
  실제 STM32 C 포함 오프로봇 시험 63개가 통과했고 F401RE 실물 flash/verify/reset도 완료했다.
  **12개 제어선 재배선·도통·모터 시험은 아직**이다.
- 4개 GitHub `main` 기준은 STM `4de305d`, Nano `ddf1b59`, RPi `7a5c99c`, Orin `5afc04d`.
  2026-08-24 Nano·RPi 실기기 배포·native build·서비스 재기동 완료. Nano는 RTSP·IMU·대시보드
  WebSocket, RPi는 자동실행·8765 리슨까지 확인했다. Nano의 STM32 USB는 현재 미연결이다.
- 경로 완료 표시는 실제 면적 커버리지를 증명하지 않는다. 엔코더 `count/m`을 측정한 뒤 작은
  0.5×0.5 m 경로부터 실제 이동 궤적을 검증한다.
- 장치별 복붙 명령: [[10. 장치별 동작 및 명령어]] · 촬영용 최소 결선: [[11. 시연용 최소 배선도]]
- Nano B01 무선랜카드 장착과 터미널 Wi-Fi 연결은 완료됐다. 현장 SSID·Tailscale 재접속은 전원
  재부팅 후 한 번 더 확인한다.

## 시스템 구성

### "서버"라는 말의 두 가지 뜻 (혼동 주의 — 보고서 작성 시 반드시 구분)
이 프로젝트에서 "서버"가 서로 다른 두 의미로 쓰인다. 섞어 쓰면 구조 설명이 무너진다.

1. **역할로서의 서버 = Jetson Orin Nano Super** — 로봇이 감당 못 하는 무거운 연산(결함탐지)을
   대신 떠맡는 쪽. 흔히 말하는 "서버"가 이것.
2. **통신 프로토콜상의 서버 = 접속을 기다리는 쪽** — 중요도·두뇌 역할과 **무관**하다. 문을 열고
   대기하면 서버, 찾아가서 접속하면 클라이언트일 뿐.

**로봇의 두뇌는 어디까지나 Jetson Nano B01이고, 대시보드(RPi4)는 WebSocket 서버이지만 두뇌도
중심도 아니다.** 보고서 표기 권장: "Orin = 영상처리 서버", "대시보드 = 관제 콘솔(WebSocket 서버 겸)".

### 구성도

```
                    [ Jetson Nano B01 ]  ← 로봇 두뇌
                     RTSP 서버(영상 제공)
                     WS 클라이언트
                      │           │
             영상 RTSP │           │ WS (상태↑ / 제어↓)
                      ↓           ↓
        [ Orin Nano Super ] ──→ [ RPi4 대시보드 ]
         연산 서버(결함탐지)   WS   WS 서버(문 열고 대기)
         RTSP 클라이언트            RTSP 클라이언트
         WS 클라이언트

              [ STM32 ] ──UART(ST-LINK VCP)── [ Nano B01 ]
               모터 4채널 PWM / 엔코더 / 거리센서 ADC
```

### 프로토콜별 서버·클라이언트

| | 서버 (기다림) | 클라이언트 (접속함) |
|---|---|---|
| 영상 (RTSP, 720p30) | Nano B01 | Orin Nano Super, 대시보드 |
| 데이터 (WebSocket) | **대시보드(RPi4)** | Nano B01, Orin Nano Super |
| 연산 (역할 구분) | Orin Nano Super | — |

전 구간 Tailscale로 묶인 무선. STM32↔Nano B01만 유선 UART.

### 대시보드를 WebSocket 서버로 둔 이유
전원 켜는 순서와 무관하게 알아서 붙게 하기 위함. 대시보드는 사람이 손에 들고 켜는 물건이라
항상 켜져 있는 쪽이고, 로봇과 오린은 부팅 후 "대시보드에 접속 시도"만 반복하면 되며 끊겨도
재접속만 하면 된다. 반대로 Nano B01을 서버로 두면 대시보드·오린이 각각 로봇의 상태를 살펴
접속해야 하고, **오린 → 대시보드 방향 연결이 로봇을 경유하거나 별도로 또 필요해진다.**
현재 구조는 데이터의 최종 목적지(사람이 보는 화면)가 곧 서버라 연결이 한 곳으로 모인다.
