# 구현 계약 — ROS2 노드·토픽·메시지 정본

[[3. 소프트웨어/04. 센서-안전감시 구현명세]]와 [[3. 소프트웨어/05. 반자율 전면점검 구현명세]]는
**무엇을 왜 만드는가**의 정본이다. 두 문서는 UART 프레임·상태머신·시험·촬영까지 정해 놓았지만,
**나노 B01 내부의 ROS2 노드 이름·토픽 이름·메시지 타입**은 정하지 않았다. 그대로 두면 구현자가
매번 추측하게 되고, 특히 `dashboard_bridge`가 이미 기대하고 있는 계약과 어긋나면 화면이 조용히
빈칸으로 남는다 — **지금 IMU가 정확히 그 상태다.**

이 문서는 **그 빈 곳만** 채운다. 04·05와 충돌하면 04·05가 우선이며, 이 문서를 고쳐 맞춘다.

관련: [[3. 소프트웨어/01. STM32]] · [[3. 소프트웨어/02. 젯슨]] · [[3. 소프트웨어/03. 대시보드]]

## 0. 바꾸면 안 되는 것

구현 중 편의로 아래를 바꾸면 다른 기기가 조용히 깨진다. 바꿔야 하면 **이 문서를 먼저 고치고**
양쪽 계약시험을 동시에 추가한다.

- STM32↔Nano 상행 거리 프레임 `BB 01 d1 d2 d3 flags xor 55` (8바이트)
- STM32↔Nano 하행 제어 프레임 `AA CMD throttle turn xor 55` (6바이트)
- 엔코더 프레임 `BC 02 left_i32 right_i32 flags xor 55` (13바이트, 05 §8 신설)
- 보정용 원시 ADC 프레임 `BD 03 adc1_u16 adc2_u16 adc3_u16 flags xor 55`
  (11바이트, little-endian). Nano는 `/silorobot/distance_adc` (`UInt16MultiArray`)로 발행한다.
- 배터리 프레임 `BE 04 vbat1_mv_u16 vbat2_mv_u16 flags xor 55` (9바이트, little-endian, §7-1)
- WebSocket `status` JSON의 기존 키 `imu` / `distance` / `connected`
- 대시보드 제어 메시지 `move` / `stop` / `stop_release`
- 거리값 `0` = "유효하지 않음" (미보정·읽기실패·범위밖)

## 1. 현재 ROS2 그래프 (2026-08-19 코드 실측)

```text
dashboard_bridge     발행: /silorobot/drive_command      geometry_msgs/Twist
                     발행: /silorobot/emergency_stop     std_msgs/Bool
                     구독: /silorobot/battery_voltage    std_msgs/Float32    ← 발행자 없음
                     구독: /silorobot/imu                sensor_msgs/Imu     ← 발행자 없음
                     구독: /silorobot/distances_mm       std_msgs/UInt8MultiArray
                     구독: /silorobot/stm32_connected    std_msgs/Bool

stm32_uart_bridge    발행: /silorobot/distances_mm
                     발행: /silorobot/stm32_flags        std_msgs/UInt8
                     발행: /silorobot/stm32_connected
                     구독: /silorobot/drive_command
                     구독: /silorobot/emergency_stop

camera_rtsp_server   ROS 토픽 없음 (GStreamer RTSP 서버만)
```

**2026-08-23 현재 두 빈 곳은 코드로 채웠다.** IMU는 실물 UART 검증, 배터리는 분압 회로
배선·보정과 `BATTERY_MONITOR=1` 빌드만 남았다.

- **IMU**: `imu_node`를 새로 만든다 (§4)
- **배터리**: 2026-08-19 전원부 확정으로 **STM32 ADC 분압 측정이 결정**됐다
  ([[2. 하드웨어/04. 전원]], [[02. 결정로그]]). STM32가 `0xBE` 프레임으로 올리고
  `stm32_uart_bridge`가 `/silorobot/battery_voltage`로 발행한다 (§7-1).
  `dashboard_bridge`가 대표 전압·팩별 mV·flags를 status의 `battery`/`battery_meta`에 싣는다.

## 2. 목표 ROS2 그래프

```text
[imu_node] ─────────────────────► /silorobot/imu
                                  /silorobot/imu_health

[stm32_uart_bridge] ────────────► /silorobot/distances_mm
                                  /silorobot/stm32_flags
                                  /silorobot/stm32_connected
                                  /silorobot/wheel_counts      (05 엔코더, B단계)
                    ◄──────────── /silorobot/drive_command
                    ◄──────────── /silorobot/emergency_stop

[safety_supervisor] ────────────► /silorobot/safety_state
                                  /silorobot/emergency_stop    ← 최종 STOP 결정 주체
                    ◄──────────── /silorobot/imu
                    ◄──────────── /silorobot/imu_health
                    ◄──────────── /silorobot/distances_mm
                    ◄──────────── /silorobot/stm32_flags
                    ◄──────────── /silorobot/stop_request      ← 사람의 의도

[dashboard_bridge] ─────────────► /silorobot/drive_command
                                  /silorobot/stop_request      ← 변경: 직접 STOP 안 함
                   ◄──────────── /silorobot/imu
                   ◄──────────── /silorobot/distances_mm
                   ◄──────────── /silorobot/stm32_connected
                   ◄──────────── /silorobot/safety_state
```

### 이 구조의 핵심 — STOP의 단일 결정 주체

04 §7은 *"stop_release는 해제 요청일 뿐이고, Nano는 센서가 안정된 경우에만 래치를 푼다"*고
정했다. 그런데 현재 `dashboard_bridge`는 사용자의 해제를 **`/silorobot/emergency_stop`에 곧장
False로 발행**한다. 즉 센서가 위험해도 화면 버튼만 누르면 풀린다.

그래서 사람의 의도를 `/silorobot/stop_request`로 분리하고, **`/silorobot/emergency_stop`은
`safety_supervisor`만 발행**한다. 자동 위험정지와 수동 정지가 한 곳에서 합류하고, 해제는
"사용자가 원했다 **그리고** 센서가 안정됐다"일 때만 나간다.

`stm32_uart_bridge`는 지금 코드 그대로 두면 된다 — 구독하는 토픽 이름이 안 바뀐다.

### 커스텀 메시지를 만들지 않는다 — 결정과 근거

`safety_state`·`imu_health`처럼 구조가 있는 데이터를 **`std_msgs/String`에 JSON 문자열로**
싣는다. 정석은 커스텀 `.msg` 패키지지만:

- ROS2 **Eloquent**에서 커스텀 메시지 패키지를 추가하면 빌드·의존성 작업이 늘고, Nano 실기에서
  깨졌을 때 디버깅 비용이 마감(8/25) 대비 크다
- 이 데이터의 **유일한 최종 소비자가 WebSocket JSON**이다. 어차피 JSON으로 직렬화된다
- `ros2 topic echo`로 사람이 바로 읽을 수 있어 실기 디버깅이 빠르다

대신 **JSON 스키마를 이 문서에 고정**하고 계약시험으로 강제한다. 프로젝트가 길어지면 커스텀
메시지로 옮기는 게 맞고, 그때 바꿀 지점은 이 표 한 곳이다.

## 4. `imu_node` 명세 (신규)

**파일**: `src/silorobot_nano/silorobot_nano/imu_node.py`
**실행**: `ros2 run silorobot_nano imu_node --ros-args -p port:=/dev/ttyTHS1 -p baud_rate:=9600`

### 배선 — Nano GPIO UART 직결 (현재 정본)

WT901C를 Nano B01 40핀 헤더의 3.3 V TTL UART에 직접 연결한다. FT232는 현재 구성에서 쓰지 않는다.

```text
WT901C                  Nano B01 40핀
  TX   ───────────────► 10번 UART RX
  RX   ◄───────────────  8번 UART TX
  VCC  ◄───────────────  1/17번 3.3V
  GND  ────────────────  6/9/14/20번 GND 중 하나
```

- **VCC는 3.3V**이며 Nano 5V 핀(2/4번)에 연결하지 않는다.
- TX↔RX **교차 연결**이다. 같은 이름끼리 연결하면 데이터가 들어오지 않는다.
- 장치명은 `/dev/ttyTHS1`. `dialout` 그룹 필요(STM32 VCP와 동일)
- WT901C 기본 baud는 **9600**이며 설정으로 115200까지 올릴 수 있다. 실물 확인 우선

`/dev/ttyTHS1`은 `nvgetty`가 점유할 수 있으므로 최초 1회 `sudo systemctl disable --now nvgetty`
후 재부팅한다. FT232를 임시 진단에 사용할 수는 있지만, 그러면 포트 인자를 `/dev/ttyUSB0`으로
명시해야 하며 현재 자동실행 설정과 달라진다.

**연결 확인** (노드 작성 전 반드시 먼저):

```bash
ls -l /dev/ttyTHS1
groups
timeout 5 xxd -g1 /dev/ttyTHS1 | head -20
```

`55 51` / `55 52` / `55 53`으로 시작하는 11바이트 반복이 보이면 WIT 표준 프레임이다.
**다르면 아래 변환식을 억지로 적용하지 말고 실제 프레임을 먼저 파악한다** (04 §6).

### 파라미터

| 이름 | 기본값 | 설명 |
|---|---|---|
| `port` | `/dev/ttyTHS1` | GPIO UART 정본. FT232 임시 사용 시 `/dev/ttyUSB0`으로 덮어쓰기 |
| `baud_rate` | `9600` | WT901C 기본값. 실측 우선 |
| `reconnect_sec` | `2.0` | `stm32_uart_bridge`와 동일 패턴 |
| `publish_hz` | `20.0` | 파싱은 수신 즉시, 발행은 이 주기로 다운샘플 |
| `stale_ms` | `300` | 이보다 오래된 샘플이면 유효하지 않음 |

### 파싱

04 §6을 그대로 따른다. **실물 hex dump 확인이 선행 조건**이며, WIT 표준 11바이트 프레임으로
확인된 경우에만 아래를 적용한다.

```text
프레임: 0x55 [type] [payload 8B] [checksum]
checksum = frame[0..9] 합의 하위 8비트

0x51 acceleration  = int16 / 32768 * 16    (g)
0x52 angular rate  = int16 / 32768 * 2000  (deg/s)
0x53 angle         = int16 / 32768 * 180   (deg)
```

- 헤더 재동기화: 버퍼에서 `0x55`를 찾아 11바이트로 끊고, checksum 실패 시 1바이트 밀어 재시도
- `0x51` / `0x52` / `0x53` 셋이 모두 최소 1회 들어온 뒤부터 발행 시작
- checksum 실패율을 카운트해 `imu_health`로 보고 (배선·노이즈 진단용)

### 발행 — `/silorobot/imu` (`sensor_msgs/Imu`)

- `header.stamp` = 수신 시각. **소비자는 이 값으로 age를 계산한다**
- `header.frame_id` = `imu_link`
- `orientation` = **Euler(roll·pitch·yaw)를 쿼터니언으로 변환해 채운다**
  - `dashboard_bridge._quaternion_to_euler()`가 이미 이 값을 다시 오일러로 되돌린다.
    **이 왕복 계약을 깨지 말 것** — 여기가 지금 화면 빈칸의 원인 지점이다
  - 변환은 ZYX 순서(yaw → pitch → roll), 라디안 입력
- `angular_velocity` = gx·gy·gz를 **rad/s로 변환**해서 채운다 (ROS 표준 단위)
- `linear_acceleration` = ax·ay·az를 **m/s²로 변환**해서 채운다 (g × 9.80665)
- covariance는 미측정이므로 `[0] = -1`로 두어 "모름"을 명시한다
- **유효하지 않으면 발행하지 않는다.** 마지막 stamp가 오래되면 소비자가 stale로 판정한다

> 화면 표시는 도(°) 단위이므로 도↔라디안 변환 지점을 한 곳에 모아 두고 단위를 주석으로 남길 것.
> **단위 혼동이 이 노드에서 가장 나오기 쉬운 버그다.**

### 발행 — `/silorobot/imu_health` (`std_msgs/String`, JSON)

```json
{
  "connected": true,
  "port": "/dev/ttyTHS1",
  "sample_hz": 19.8,
  "checksum_error_rate": 0.001,
  "last_sample_age_ms": 12,
  "valid": true,
  "types_seen": ["0x51", "0x52", "0x53"]
}
```

### 실패 거동

- 포트 없음·권한 없음: `reconnect_sec` 간격 재시도, `connected=false`, **노드는 죽지 않는다**
- checksum 실패 폭증: 발행은 계속하되 health의 `valid=false`, 에러율 노출
- **IMU가 없어도 이동 제어는 계속 되어야 한다.** imu_node 부재가 주행을 막으면 안 된다

## 5. `safety_supervisor` 명세 (신규)

**파일**: `src/silorobot_nano/silorobot_nano/safety_supervisor.py`

판정 로직·임계값·상태 전이는 **04 §8~§10이 정본**이다. 여기서는 인터페이스만 고정한다.

### 발행 — `/silorobot/safety_state` (`std_msgs/String`, JSON)

```json
{
  "state": "NORMAL",
  "reasons": [],
  "latched": false,
  "armed": false,
  "since_ms": 0,
  "distance_meta": {
    "valid": [true, true, true],
    "unit": "mm",
    "calibrated": false,
    "mean": 50.0,
    "spread": 2.0,
    "mean_rate": 0.0,
    "age_ms": 0
  },
  "imu_meta": {
    "valid": true,
    "age_ms": 12,
    "gyro_mag_dps": 3.1
  },
  "stm32": {
    "connected": true,
    "stop_latched": false,
    "timeout_seen": false
  }
}
```

- `state`: `NORMAL` / `WARNING` / `STOPPED` (04 §9)
- `reasons`: 짧은 코드 배열. 예 `["spread_high", "gyro_spike"]`
- `calibrated`: 거리 LUT 보정 전이면 `false`. **이때 대시보드는 단위를 `mm`로 쓰지 않는다** (04 §5)

### 발행 — `/silorobot/emergency_stop` (`std_msgs/Bool`)

- **이 토픽의 유일한 발행자다.**
- 위험 판정 또는 사용자 정지 → `True`를 **위험이 지속되는 동안 반복 송신**
  (한 번만 보내면 STM32 재부팅·프레임 손실 시 풀린다)
- 해제는 **사용자가 요청했고 그리고 센서가 안정**일 때만 `False`
- 해제를 거부하면 `safety_state.reasons`에 사유를 남겨 화면에 뜨게 한다

### 구독

`/silorobot/imu`, `/silorobot/imu_health`, `/silorobot/distances_mm`,
`/silorobot/stm32_flags`, `/silorobot/stop_request`

### 안전 원칙

- **센서가 없거나 stale이면 "안전"으로 간주하지 않는다.** IMU 미발행 상태에서 거리 편차만으로
  판정할 수 있으면 하고, 둘 다 없으면 `armed=false`로 감시 비활성을 **명시**한다.
  조용히 `NORMAL`을 보내지 말 것
- 판정 주기는 10Hz 이상. STOP 반복 송신은 판정 주기와 별개로 유지
- **RPi4가 죽어도 이 노드는 STOP을 보낼 수 있어야 한다** (04 §4)

## 6. `dashboard_bridge` 변경 명세

기존 파일 수정. 변경은 세 가지뿐이다.

1. **`stop` / `stop_release` 수신 시 `/silorobot/emergency_stop` 대신
   `/silorobot/stop_request`(Bool)를 발행**한다 (`stop` → `True`, `stop_release` → `False`)
2. `/silorobot/safety_state`를 구독해 status JSON에 `safety` / `distance_meta` / `stm32`
   블록을 합친다. **JSON 스키마는 04 §7 v2가 정본**
3. `battery`는 측정 주체가 없으므로 **항상 `null`**. 가짜 전압 금지

`imu` 객체에 `gx/gy/gz/ax/ay/az/valid/age_ms`를 추가한다 — 값은 `/silorobot/imu`와
`/silorobot/imu_health`에서 채운다. **기존 `roll/pitch/yaw` 키는 그대로 둔다** (하위 호환, 04 §7).

---

## 7. STM32 엔코더 + `wheel_counts` (05 B단계)

핀·타이머·보정 절차는 **05 §7이 정본**이다. 여기서는 나노 쪽 계약만 고정한다.

- STM32는 05 §8의 13바이트 `BC 02 ...` 프레임을 20Hz로 추가 송신
- `stm32_uart_bridge`는 **헤더별 고정길이로 분리 파싱**한다
  (`0xBB` → 8바이트 거리, `0xBC` → 13바이트 엔코더, `0xBD` → 11바이트 원시 ADC).
- 파싱 결과를 `/silorobot/wheel_counts` (`std_msgs/Int32MultiArray`, `data=[left, right]`)로 발행
- **누적 카운트를 그대로 싣는다.** 나노가 차분을 계산한다 (프레임 손실 복구가 쉬움, 05 §8)
- 엔코더 flags는 `/silorobot/stm32_flags`와 **섞지 않는다**. 별도 필드가 필요하면 이 문서를 먼저 고칠 것

---

## 7-1. 배터리 전압 — `0xBE` 프레임 (전원부 확정 반영)

회로·임계값·보정 절차는 **[[2. 하드웨어/04. 전원]]이 정본**이다. 여기서는 프레임과 토픽만 고정한다.

```text
[0xBE][0x04][vbat1_mv_u16_le][vbat2_mv_u16_le][flags][xor][0x55]   9바이트, 1~2Hz

flags  bit0 = vbat1 유효
       bit1 = vbat2 유효
       bit2 = 저전압 경고 (어느 한 팩이라도 10.5V 이하)
       bit3 = 저전압 정지 래치 (어느 한 팩이라도 9.9V 이하)
       bit4 = 배터리 감시 펌웨어 활성 (`BATTERY_MONITOR=1`)
       나머지 예약
```

- 전압은 **mV 단위 uint16** (12600 = 12.6V). 측정 실패·미연결은 `0` + 해당 valid 비트 0
- **헤더 `0xBD`는 거리 보정용 원시 ADC가 이미 쓰고 있다.** 배터리는 `0xBE`다 — 혼동 금지
- 배터리는 빠르게 변하지 않으므로 20Hz가 아니라 **1~2Hz**로 충분하다

### Nano 쪽 처리

- `stm32_uart_bridge`가 `0xBE`를 파싱해 **`/silorobot/battery_voltage`(`std_msgs/Float32`)** 로
  발행한다. 값은 **두 팩 중 낮은 쪽**을 쓴다 — 화면 한 칸에 대표값을 보여야 하고, 안전 관점에서
  낮은 쪽이 기준이기 때문
- 팩별 값과 flags는 `safety_supervisor`가 `safety_state.battery_meta`에 싣는다. bit4가 켜졌는데
  어느 한 팩이 무효이거나 상태가 stale이면 정지 해제를 거부한다.
- bit3는 과거 저전압 정지 래치이므로 그 비트 자체로 해제를 막지 않는다. 두 팩 현재값이 모두
  `battery_release_mv=10200` 이상일 때만 Nano가 해제 명령을 보내고, STM32가 bit3를 지운다.
  bit3를 해제 거부 조건으로 쓰면 해제 명령 전까지 bit3가 남는 구조와 순환해 영구 교착된다.
- **저전압 정지는 STM32가 자체 판단한다.** Nano는 표시·기록만 하고 정지 결정을 대신하지 않는다
  (통신이 끊겨도 STM32 혼자 끊을 수 있어야 하므로)

## 8. 반자율 노드 (05, 마지막 단계)

05가 정본이며, 노드 경계만 고정한다.

| 노드 | 발행 | 구독 |
|---|---|---|
| `odometry_node` | `/silorobot/pose` (String JSON: x, y, theta, conf) | `/silorobot/wheel_counts`, `/silorobot/imu` |
| `coverage_planner` | `/silorobot/plan` (String JSON) | 계획 요청 (dashboard_bridge 경유) |
| `path_follower` | `/silorobot/drive_command`, `/silorobot/mission_state` (String JSON) | `/silorobot/pose`, `/silorobot/plan`, `/silorobot/safety_state` |

- `path_follower`는 **`/silorobot/drive_command`의 두 번째 발행자**가 된다. 수동 조작과 충돌하지
  않도록 **모드 전환 시 한쪽만 발행**한다. 두 발행자가 동시에 20Hz로 쏘면 마지막 것이 이기는
  비결정적 동작이 된다 — 05 §11 상태머신에서 모드를 단일화할 것
- 구현 규칙(2026-08-20): `dashboard_bridge`는 `/mission_state.mode`를 추적하고 `AUTO` 동안
  대시보드의 `move`를 폐기한다. `route_start` 수신 즉시 AUTO guard를 세우고 `route_cancel`과
  mission의 MANUAL 복귀 때만 수동 발행을 다시 허용한다. pause/cancel 전환에는 0 명령을 1회 즉시
  발행한다.
- `path_follower`는 `safety_state.state != NORMAL`이면 **즉시 발행을 멈춘다**
- WebSocket status에는 기존 필드와 함께 `plan` 및 `mission`을 실어 RPi4가 가짜 타이머 없이
  실제 `plan_id`, `state`, `current_waypoint`, `total_waypoints`, `coverage_ratio`를 표시한다.

## 11. 계약시험 (하드웨어 없이 도는 것만)

- `imu_node`: 알려진 WIT 프레임 바이트열 → 기대 roll/pitch/yaw·각속도·가속도.
  **checksum 실패 프레임을 섞어도 재동기화되는지**
- `imu_node`: Euler → 쿼터니언 → (`dashboard_bridge` 함수) → Euler 왕복이 오차 내 일치.
  **이 시험이 화면 빈칸 재발을 막는 핵심이다**
- `safety_supervisor`: 합성 센서 시퀀스 → 기대 상태 전이. 특히 **조건 정상화 후에도 latched 유지**,
  해제 거부 경로
- `safety_supervisor`: 센서 stale → `armed=false`이지 `NORMAL`이 아님
- `stm32_uart_bridge`: `0xBB`·`0xBC`가 섞여 들어와도 각각 정확히 분리, 경계에서 잘린 프레임 복구
- `dashboard_bridge`: 04 §7 v2 JSON이 스키마대로 나오는지, 신규 필드 없이도 구버전 키 유지
- STM32 `tests/test_main.c`: 거리 LUT 경계값(19·20·150·151mm), 데드존 매핑
