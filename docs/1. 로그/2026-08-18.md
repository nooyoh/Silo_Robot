## 임시 랜선 직결로 카메라(RTSP) 최초 확인 성공

- 설정 과정에서 삽질 몇 개 있었음:
  1. 라파 `eth0`는 케이블 연결은 인식(`LOWER_UP`)해도 IP가 안 잡혀 있었음 — DHCP로 기다리는
     상태(`connecting (getting IP configuration)`)였고, 나노 쪽에 DHCP 서버가 없으니 영영 안
     잡힘. `nmcli connection modify 'Wired connection 1' ipv4.method manual ipv4.addresses
     192.168.50.20/24` + `connection up`으로 고정 IP 강제 지정해야 했음.
  2. 라파에서 나노까지는 SSH 직접(Claude Code 세션)은 안 됨 — 이 도구가 도는 PC가 192.168.50.x
     대역에 물리적으로 없기 때문. **라파 경유(`ssh <라파> → ssh <나노>`)로 점프**해야 함.
  3. 나노 쪽도 eth0에 `192.168.50.10` 고정 IP를 똑같이 잡아줘야 링크 양쪽이 통신됨(한쪽만
     해서는 안 됨) — 사용자가 나노에 직접(모니터+키보드) 접속해 처리.
  4. 라파→나노 SSH가 처음엔 `ssh-copy-id`로 "no identities found" 에러 — **라파 자체에 나갈 때
     쓸 키가 없었음**(들어오는 `authorized_keys`만 있고 자기 키페어가 없었음). `ssh-keygen`으로
     라파에 키 생성 후 `ssh-copy-id` 재시도로 해결, 이후 라파→나노 무비밀번호 SSH 확립.
- 나노 B01에서 카메라 RTSP 서버 노드(`ros2 run silorobot_nano camera_rtsp_server`, 기존
  ROS2 코드 그대로) 수동 기동 → `192.168.50.10:8554`에서 정상 대기 확인(`ss -tlnp`).
- 라파에서 `gst-launch-1.0`으로 스트림 수신 테스트 → PLAYING 상태까지 정상 진입, 영상 데이터
  자체는 전달 확인됨.
- 라파 대시보드 앱을 `--rtsp rtsp://192.168.50.10:8554/robot`로 재실행 → **사용자가 라파 화면에서
  실제 영상 확인함 ("영상 잘나와").** 나노 B01 카메라 → 대시보드 영상 표시 파이프라인이 임시
  랜선 경로로나마 엔드투엔드 첫 성공.
- 확인 도중 Claude Code의 라파 SSH(Tailscale 경유) 접속이 일시적으로 끊김(라파 `amc`가
  Tailscale에서 offline으로 잡힘) — 원인 미확인이나, **영상 경로(나노↔라파 랜선 직결)는 와이파이/
  Tailscale과 무관하게 동작하므로 실제 영상 확인엔 영향 없었음.**

**다음에 할 것**: 이 임시 경로 확인은 카메라(RTSP) 단일 구간만 검증됨. WebSocket(제어·상태·
결함탐지) 구간, STM32/모터 통합은 이번 세션 스코프 밖(사용자가 "모터 빼고"로 명시). 인터넷이
생기면 Tailscale IP로 원복하고 재검증 필요.

## WebSocket 제어/상태 채널도 같은 날 확인 성공

- 나노 B01에서 `dashboard_bridge` ROS2 노드를 `--ros-args -p
  dashboard_uri:=ws://192.168.50.20:8765` 파라미터로 기동(기본값은 Tailscale IP라 임시 링크용
  으로 오버라이드 필요했음).
- `ss -tnp`로 라파↔나노 간 WebSocket 연결이 `ESTABLISHED` 상태임을 확인, **사용자도 대시보드
  화면 상단 "로봇 연결" 배지가 켜진 것을 확인함.**
- 관련 ROS2 토픽(`/silorobot/battery_voltage`, `/silorobot/imu`, `/silorobot/distances_mm`,

  토픽들에 실제 값을 채워줄 발행자(STM32 브릿지)가 안 떠 있어 대시보드의 배터리·IMU·거리센서
  표시는 비어있는 게 정상 — 버그 아님.
- 이동 명령(터치 조작 → `/silorobot/drive_command` 토픽 실시간 확인)까지는 이번 세션에서 검증
  안 하고 저장 시점에서 멈춤 — 다음에 이어서 할 수 있음.

**요약**: 오늘 하루 만에 임시 랜선 경로로 **RTSP 영상 + WebSocket 제어/상태 채널 둘 다** 엔드투

### 보드가 F401RE가 아니라 **F411RE**였다

- 빌드가 F401 전용이라 `stm32f411xe.h`·`startup_stm32f411xe.s`가 필요했는데, GitHub 레포는
  `.gitignore`로 그 파일들을 빼놨었음. **아직 안 지운 볼트 사본(`stm32-f401re/`)에서 꺼내 해결.**
- Makefile을 `DEVICE=f401`(기본)/`DEVICE=f411`로 보드 선택 가능하게 수정, F411용 링커스크립트
  (RAM 128K) 추가. 커밋 `fb690d0` push 완료.
- 두 보드는 NUCLEO-64 핀아웃이 같고 이 펌웨어가 쓰는 TIM2/3/4·USART2·ADC1·GPIO 레지스터도
  동일해 **`docs/pinmap.md`는 양쪽에 그대로 유효**. 배선 다시 안 해도 됨.

### 플래시
- `STM32_Programmer_CLI`(CubeIDE 동봉)로 SWD 플래시. Device ID `0x431`(STM32F411xC/E) 인식,
  검증 통과. **레포에 `.cproject`가 없어 CubeIDE 임포트는 설정을 손으로 만들어야 하므로 CLI가 빠름.**
- Flash 11,472B / RAM 1,976B.

### 모터 첫 구동 — 성공
- 정지 래치 때문에 플래시만으로는 안 돌아, PowerShell 시리얼 송신 스크립트를 만들어 20Hz로
  프레임 전송(`D:\SiloRobot\_tools\motor_test.ps1`). **모터 4개 전부 회전 확인.**
- **`throttle=20`에서 이미 회전** — 데드존은 20% 미만. 정확한 값은 더 낮춰가며 재측정 필요.
- **방향 전환 시 순간 전류 1.7A까지 상승** (파워서플라이 관측). **단, 무부하 벤치 값이므로
  등반 부하 사이징 근거로 쓰면 안 됨** — 모터 정격은 개당 1.6A, 스톨 6.5A.
- 배터리 여유 검토: 11.1V 2200mAh 70C = 이론 154A라 전류는 전혀 문제 아님. 실제 제약은 구동시간
  (4개 정격 6.4A 기준 약 16~20분)과 **드라이버 12A·XT60 16AWG 배선**. 좌우로 배터리를 나누면
  두 팩의 (−)를 STM32 GND와 공통으로 묶어야 해 순환전류 문제가 생기므로 **한 팩으로 4개 구동
  + 두 번째 팩은 예비**를 권장.

### 좌우 회전 방향 — 배선으로 고치기로
- 펌웨어는 좌우에 **동일 극성**을 보낸다(`silo_motor_driver.c`에 좌우 반전 없음).
  믹싱은 표준 아케이드(`left=throttle+turn`, `right=throttle-turn`).
- 실측: `throttle`만 주면 좌우가 **반대**로, `turn`만 주면 좌우가 **같은 방향**으로 회전 →
  **한쪽 배선이 뒤집혀 있다는 뜻으로 완전히 일관됨.** 소프트웨어 정상.
- 궤도 로봇은 좌우 모터가 거울처럼 장착되므로 **한쪽 `M_A`/`M_B`를 바꿔 끼우는 게 표준 해법**.
  사용자가 배선에서 고치기로 결정(펌웨어에 반전 플래그 추가하지 않음).
- **판정 기준은 장착 후**: `throttle=+`일 때 양쪽 궤도가 로봇을 같은 방향으로 밀면 정답.

### 라파 → 나노 → STM32 전 구간 연결
- 나노 계정은 **`jetson@ubuntu`** (볼트에 안 적혀 있어 헤맴 — 이제 기록함).
- `/dev/ttyACM0` **Permission denied** — `jetson`이 `dialout` 그룹에 없었음.
  임시로 `sudo chmod a+rw /dev/ttyACM0`, 영구 해결은 `sudo usermod -aG dialout jetson`(재로그인).
- 대시보드 터치 → `/silorobot/drive_command` 토픽에 값 도달 확인(`linear.x: 5.0`).
  **대시보드 → 나노 구간 검증 완료** (08-17 세션에서 미검증으로 남겼던 항목).
- 그런데 **모터는 안 돌았음** — 원인 2개:
  1. **정지 해제 프레임이 한 번도 안 나감** (아래 버그, [[03. 트러블슈팅]])
  2. 터치 값이 `linear.x: 5.0` = throttle 5%로 **데드존 미만**

### 발견·수정한 버그: 정지 래치 상태 불일치
- `stm32_uart_bridge.py`가 `_emergency_latched = False`로 시작하는데 **STM32는 부팅 직후
  래치 상태**. 대시보드가 `stop_release`를 보내도 `_on_emergency_stop`의 `elif
  self._emergency_latched:`가 거짓이라 통과 → **`CMD_STOP_RELEASE(0x03)`가 영원히 안 나감.**
- 현장 우회: 대시보드에서 **정지 버튼 한 번 → 해제** (True를 거쳐야 elif가 걸림).
- 수정: 초기값을 `True`로 바꾸고, **시리얼 재연결 시에도 다시 래치로 간주**(재연결 = STM32가
  재부팅됐을 수 있음). 명시적 해제 전엔 안 움직이는 안전 설계는 유지. 커밋 `6da485c` push 완료.

  (실제로 `-Turn` 파라미터가 인식 안 됨). BOM 포함 UTF-8로 저장하거나 주석을 영문으로 쓸 것.
- ROS2 노드는 포그라운드로 도는 게 정상 — 터미널을 여러 개 여는 방식이 맞다.
