## 대시보드 개발 방향 확정 (구술 그대로)

이 채팅방(세션)은 라즈베리파이4만 다룬다. OS는 이미 새로 깔았음([[1. 로그/2026-08-14]] 참조).
이 채팅방의 최종 목표는 대시보드 만들기.

- 개발 스택: C++ + Qt. 이유 — 영상 실시간 처리해야 하는데 성능을 생각해서 (웹앱/Python 등은
  명시적으로 비교하지 않고 성능 우려로 배제).
- 로봇(Jetson Nano B01) ↔ 라즈베리파이 대시보드 통신: 무선. Tailscale로 두 기기를 같은
  네트워크로 묶은 뒤 통신할 예정.
- 화면에 넣을 기능: 원격 모니터링 + 제어 "둘 다 최소 기능으로" 우선 구현.

**이번 세션은 여기까지 — 실제 구현(Qt 프로젝트 셋업, Tailscale 설치 등)은 이 세션 토큰 소진으로
못 함. 다음은 코덱스(Codex)나 다른 세션에서 이어감.** 인수인계 상세는
[[00. LLM작업규약]] §5 참조.

## Orin Nano Super 영상 서버 방향 확정 (구술 그대로, 별도 세션)

이 채팅방(세션)은 젯슨 오린 나노 Super만 다룬다. 최종 목표는 영상 서버(Nano B01로부터 영상
수신 + 카메라 비전 기반 결함탐지 + 대시보드로 결과 전달) 소프트웨어 만들기. 코드는 안 짜고
확정만 진행.

- 결함탐지 방식: YOLOv8s를 AI Hub 균열 데이터셋([[99. ETC]] 후보)으로 파인튜닝 → TensorRT로
  변환해 Orin에서 추론. 학습은 사용자 노트북(Victus, RTX 4060)에서, 추론만 Orin에서 수행.
  모델 크기(n vs s)는 "학습은 어차피 노트북에서 하니 추론 자원을 s에 써도 되지 않냐"는 사용자
  질문에 Claude가 s 권장(크랙처럼 작은 결함엔 s가 정확도 유리, Orin+TensorRT면 s도 실시간
  가능) → 사용자 동의로 확정.
- 잡는 결함: 크랙(균열) 위주.
- 정확도 목표: 수치 목표 없음, 1차는 "일단 동작한다" 수준.
- Nano B01 → Orin 영상 전송: RTSP (대시보드 쪽 RTSP/GStreamer/720p30 결정과 동일 방식으로
  통일, 파이프라인 재사용 목적).
- Orin → 대시보드 결과 전달: Orin이 Tailscale로 대시보드(RPi4)와 직접 WebSocket 통신, Nano B01
  경유하지 않음 (기존엔 대시보드가 Tailscale로 Nano B01과만 묶여있다고 알려져 있었으나, Orin도
  이미 Tailscale 설치·로그인·통신 가능 상태로 확인됨).
- 추론 결과 로그(사후 보고서용): Orin 로컬 파일(CSV/JSONL)로 저장, DB는 이 단계에선 과함.
- 레포 구조: Orin Nano Super용 레포 하나, 그 안에서 `inference/`(RTSP 수신+TensorRT 추론+
  WebSocket 전송, 실제 서버 코드)와 `train/`(YOLOv8 파인튜닝 스크립트) 폴더로 분리.
- Tailscale: 이미 설치·로그인 완료, 다른 기기와 통신 가능한 상태 확인됨.
- 카메라 모델/장착위치/해상도([[91. 질문지]] I절 15번)는 이 세션 스코프 밖으로 판단, 안 건드림.

**이번 세션은 여기까지 — 확정만 하고 실제 코드(레포 생성, 학습 스크립트, 추론 서버)는 짜지
않음. 다음 세션이 바로 구현 착수 가능.**

## STM32 펌웨어 방향 확정 (별도 세션, 사후 보전 기록)

     2026-08-15 관제탑 세션에서 규약 §3(덤프는 로그에 먼저) 준수를 위해 사후 보전 -->

이 채팅방은 STM32 펌웨어만 다룸. 코드는 안 짜고 질문 라운드로 확정만 진행.

- 개발환경: CubeIDE + HAL (레지스터 직접 제어·LL은 폐기)
- 모터 드라이버 2개(각 2채널)로 모터 4개 제어, 엔코더는 좌/우 앞쪽 모터에만
- PWM 듀티비 0~100% 선형 매핑 (1차 잠정, 실측 후 데드존·최대치 보정)
- Nano B01↔STM32는 ST-LINK VCP(USB, 전원+UART 겸용), 축값(throttle/turn) 그대로 전달하고
  믹싱은 STM32가 수행
- 정지는 별도 명령+래치, 통신 끊김 시 STM32 자체 타임아웃 페일세이프
- 부품표 오류 발견: DFR0601 수량이 1개로 기재돼 있었으나 실제 2개 구매
- UART 텔레그램 포맷·PWM 핀 매핑·엔코더 인터페이스 상세는 "구현하면서 정하자"고 명시적 보류

## 관제탑 점검 세션 (2026-08-15, 볼트 전체 감사)

볼트 전체 정독 후 정합성 점검. 발견·처리 내역:

- **ROS2 Humble → Foxy 정정**: Nano B01의 JetPack 4.6.x는 Ubuntu 18.04, Humble은 22.04 기반이라
  설치 경로가 없음. Docker/소스빌드는 마감 앞두고 리스크가 커서 Foxy로 확정.
- **거리센서 3점 연결 경로 정정**: SHARP GP2Y0A51SK0F는 아날로그 출력인데 Nano B01엔 ADC가 없어
  "Nano 직결" 결정이 물리적으로 불가능했음. STM32 ADC로 읽어 상행 UART 텔레메트리로 올리는
  구조로 변경(부품 추가 없음). 상행 8바이트 프레임 신설.
- 구동 시간은 "테스트·시연 가능한 수준이면 충분"으로 사용자 판단 — 목표치 별도 설정 안 함.
- DFR0601 89,100원이 2개 합산가임을 소계 검산으로 확정 — 예산 총계 변동 없음, 질문지 9-1 종결.
- 그 외 문서 정합성 정리(README 확정/미확정 섹션 재배치, PWM "2채널"→4채널 표현, 예산표
  "RTOS" 문구 주의, 규약 §5 정렬).
- 하드웨어 노트 3개(아키텍처·센서비전·전원)는 **일부러 안 채움** — 실제 조립·배선을 해보며
  채우기로 사용자가 결정.

이어서 연휴 구현 순서 확정 (구술 그대로):

- 주말에 Claude 주간 한도가 소진돼 Claude로는 구현 못 함 → **Codex에서 구현 진행 예정.**
- 순서: 0단계 걸어두기(데이터셋 다운로드 시작 / Nano B01·RPi4 Tailscale / 레포 3개 / JetPack
  버전 확인) → 1단계 대시보드 Qt6 → 2단계 STM32 펌웨어 → 3단계 Nano B01 → 4단계 Orin.
- 순서를 짠 두 원칙: ① 오래 걸리는 다운로드·설치를 먼저 걸어두고 그 사이에 코딩 ② 조립이
  아직 안 끝났으니 실물에 안 묶이는 것부터 밀어냄.
- 자르는 지점: 3단계까지가 "로봇이 움직이는 데모"(8/25 해운물류 진도율 서사 성립),
  4단계 결함탐지는 9/8 한이음까지 끌고 가도 됨.
- 상세는 [[00. LLM작업규약]] §5 최상단 항목에 전부 기록함.

## "서버" 용어 혼동 정리 (사용자 질문에서 출발)

사용자가 "오린이 서버라고 생각했는데 라파가 대시보드면 구조가 어떻게 되냐"고 물음 —
볼트에서 "서버"를 두 뜻으로 섞어 쓰고 있던 게 원인이었음. 정리해서 확정:

- **역할로서의 서버 = Orin Nano Super** (무거운 연산을 떠맡음). 사용자가 원래 생각한 그 서버가 맞음.
- **프로토콜상의 서버 = 접속을 기다리는 쪽**. 중요도·두뇌 역할과 무관. 대시보드가 서버라는 건
  이쪽 얘기일 뿐이고, **로봇의 두뇌는 여전히 Nano B01**.
- 프로토콜마다 서버가 다름: 영상(RTSP)은 Nano B01이 서버 / 데이터(WebSocket)는 대시보드가 서버.
- 대시보드를 WS 서버로 둔 실질적 이유: 전원 켜는 순서와 무관하게 붙고, 오린→대시보드 연결이
  로봇을 경유하지 않아도 됨. 데이터의 최종 목적지(사람이 보는 화면)가 곧 서버라 연결이 한 곳으로 모임.
