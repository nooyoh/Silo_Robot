## [2026-08-21] 엔코더 부호 반전 수정 자체가 θ를 완전히 고정시킨 후속 버그
- 상황: 엔코더 좌우 부호 반전(`meters_per_count_right`를 음수로) 수정 뒤에도, 반자율 주행이
  회전 속도를 70~80%까지 올려 2분을 돌려도 진행률 0%·계속 제자리 회전만 지속됨.
- 원인: `odometry_node._calibrated()`가 `right_scale > 0`을 요구하고 있었는데, 방금 그 값을
  **음수**로 바꿔놨으니 `_calibrated()`가 항상 `False`를 반환 → `_on_counts()`가
  `if not self._calibrated(): return`에서 매번 조기 종료 → **`self._pose`가 단 한 번도
  갱신되지 않고 `theta=0.0`에 영원히 고정**됨. `path_follower`는 `heading_error`가 전혀
  안 바뀌니 목표각에 절대 도달 못 하고 계속 같은 방향으로만 돎 — 회전 속도를 아무리 올려도
  절대 안 고쳐지는 게 당연했음.
- 확인: 사용자가 `ros2 topic echo /silorobot/pose`를 나노 터미널에서 직접 실행 →
  `theta: 0.0, calibrated: false`가 계속 반복되는 걸로 즉시 특정.
- 해결: `_calibrated()` 조건을 `right_scale > 0` → `right_scale != 0`으로 변경(좌우 둘 다).
  커밋 `8c80e93`.
- 교훈: **부호가 의미 있게 음수일 수 있는 파라미터를 검증할 때 `> 0`을 그대로 쓰면 안 된다.**
  스케일/보정값 계열 파라미터를 고칠 때는 그 값을 참조하는 다른 유효성 검사 코드도 같이
  훑어야 한다 — 이번엔 같은 파일 안의 함수 하나였지만 놓쳤음.

## [2026-08-21] QtQuick.Controls `Button`이 이 터치 환경에서 탭에 반응하지 않음 (핵심, 재사용 필수)
- 상황: 계획 화면 "추천 경로 생성" 버튼을 눌러도 나노 B01로 아무 메시지도 안 감. 나노 B01의
  `dashboard_bridge`·WebSocket 연결·ROS2 노드 8개 전부 정상이었고(실기 확인), 대시보드 쪽
  `sendToRobot()`/`requestRoutePlan()` C++ 코드도 정상이었음에도 재현됨.
- 진단: 나노 역할을 흉내내는 파이썬 테스트 클라이언트를 직접 만들어 대시보드가 실제로 뭘
  내보내는지 지켜봄 — 버튼을 눌러도 **대시보드가 소켓에 아무것도 안 씀**을 확인. 즉 QML의
  `onClicked` 자체가 발화하지 않고 있었음.
- 원인: 이 버튼만 유일하게 **표준 `QtQuick.Controls Button`**을 쓰고 있었음. 같은 화면의 다른
  모든 컨트롤(코너 선택 타일, 키보드 숨기기, 종료, 팝업 배경 클릭 차단용 `MouseArea` 등)은 전부
  `Rectangle + TapHandler` 패턴. 이 조합(labwc + Qt6 Wayland, 배경에 풀사이즈 `MouseArea`가
  깔린 모달 팝업)에서는 표준 `Button`의 내부 클릭 인식이 씹히는 것으로 보임 — 정확한 내부
  메커니즘(이벤트 전파 vs 그랩 우선순위)까지는 규명 못 함.
- 해결: `Button`을 `Rectangle { ... Text { ... } TapHandler { onTapped: ... } }`로 교체하니
  즉시 정상 동작. **파급 효과**: 실행 화면의 시작/취소/비상정지/해제요청 4개 버튼도 같은
  `Button`을 쓰고 있어서 함께 교체함 — 확인해보진 않았지만 같은 문제가 있었을 가능성이 높음.
- **교훈(이 프로젝트 전역 규칙으로 취급할 것)**: 이 라파 대시보드 앱에서는 **`QtQuick.Controls
  Button`을 쓰지 말고, 항상 `Rectangle + Text + TapHandler` 패턴으로 커스텀 버튼을 만들 것.**
  앞으로 새 버튼을 추가할 때 이 규칙을 기본으로 따를 것 — `Button`을 보면 일단 의심할 것.
- **부수적 교훈**: "안 된다"는 제보를 받으면 먼저 "정말 안 되는지"부터 재확인할 것 — 이번 건
  사용자가 이미 "된다"고 여러 번 말했는데 진단자가 "안 된다"는 잘못된 전제로 한참 헤맴.

## [2026-08-21] `coverage_planner`/`route_plan_request` 검증 중 — Nano ROS2 CLI가 systemd 노드와 데이터 교환 자체가 안 됨 (원인: 애드혹 CLI 한정, 실제 파이프라인은 정상)
- **후속 확인(같은 날)**: 사용자가 실제 라파 대시보드에서 "추천 경로 생성"을 눌러 화면에 경로
  도표가 정상적으로 그려지는 것을 확인함. 즉 대시보드→`dashboard_bridge`→`coverage_planner`→
  `/silorobot/plan`→`dashboard_bridge`→대시보드 전체 파이프라인은 **정상 작동한다.** 아래에 남긴
  "Fast-RTPS/docker0 데이터플레인 문제" 의심은 **내가 SSH로 띄운 애드혹 `ros2 topic pub/echo`
  CLI 프로세스에 한정된 문제였을 가능성이 높다** — systemd로 같이 뜬 launch 그룹 내부의 노드끼리는
  통신이 되는 것으로 보임. CLI로 다시 검증할 일이 있으면 이 구분(애드혹 프로세스 vs 같은 launch
  그룹)을 먼저 의심할 것.
- 상황: 라파 "추천 경로 생성" 버튼을 눌러도 `/silorobot/route_plan_request`가 안 잡힌다는 제보를
  받아 `ros2 topic pub/echo`로 직접 검증하려 했으나, **재부팅 직후 깨끗한 상태에서도** 내가 SSH로
  새로 띄운 `ros2 topic pub`과 `ros2 topic echo`가 서로 데이터를 전혀 주고받지 못했다. 방향을
  바꿔서(내 CLI → 이미 떠 있는 노드, 이미 떠 있는 노드 → 내 CLI) 둘 다 실패. `safety_state`처럼
  주기적으로 발행되는 게 확실한 토픽조차 못 받았다.
- 시도한 것: `ros2 daemon stop/start`(캐시 초기화), `ROS_LOCALHOST_ONLY=1`(멀티캐스트 인터페이스
  문제 배제), 나노 완전 재부팅(누적 상태 배제) — **전부 증상 동일**. `ros2 node list`/`topic list`는
  정상 조회됨(디스커버리 캐시는 살아있음) — **디스커버리(참가자 존재 확인)는 되는데 실제 데이터
  플레인만 막힌 것으로 보임.**
- 원인 후보 (미확인): 이 나노에 `eth0`(학교망 172.20.32.x) · `tailscale0` · `docker0`(172.17.0.1)가
  동시에 떠 있음 — Fast-RTPS(ROS2 Eloquent 기본 RMW)가 discovery locator에 도달 불가능한
  인터페이스(특히 `docker0`)를 잘못 광고하면 이런 "존재는 보이는데 데이터는 안 옴" 증상이 날 수

  자체 문제일 가능성도 있음(`/dev/shm`엔 용량 여유 있고 이상한 파일 `PHS-3831`/`PHS-4035` 존재,

- **중요 — 아직 결론 아님**: 이게 `coverage_planner` 코드 버그가 아니라 **환경/RMW 문제일 가능성이

  launch와 같은 프로세스 그룹에서 테스트)으로 재현되는지 먼저 확인.
- 해결: 안 함. `docker` 제거/`docker0` 비활성화, `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`로 교체
  시도, 또는 systemd 프로세스 내부에서의 pub/sub 검증이 다음 후보.
- 부수적으로 확인된 것 (버그 아님): `coverage_planner.py`는 단위 변환 없이 순수 m 단위로만
  계산하고, 라파 QML 기본값(너비 12m·높이 8m·점검폭 0.4m·중첩 20%)을 그대로 쓰면 스트라이프
  37개가 수학적으로 정상이다 — 명세서의 "6구간 안팎"은 소형 시험판(1m×1.5m) 예시 기준.
- 별개로: 라파 대시보드 앱이 이 세션 도중 재부팅 후 꺼져 있었고, SSH로 두 번 수동 기동한 것도
  15~17초 만에 에러 로그 없이 조용히 죽었다(OOM 아님, 원인 미확인) — 부팅 시 자동 기동

## [2026-08] Qt Quick `Popup.anchors`는 `centerIn`만 지원함
- 상황: 팝업을 화면 중앙 대신 상단에 붙이려고 `anchors.top: Overlay.overlay.top; anchors.topMargin:
  2`를 썼더니 QML 로드 자체가 실패("Cannot assign to non-existent property topMargin").
- 원인: `Popup`은 `Item`을 상속하지 않고, 내장 `anchors` grouped property는 **`centerIn` 하나만
  제공**함(`top`/`left`/`margins` 등 일반 Item의 anchors 전부 없음).
- 해결: 상대 위치가 필요하면 `x`/`y`를 직접 계산해서 지정. 예:
  `x: (Overlay.overlay.width - width) / 2; y: 2`.
- 결과: 정상 로드·원하는 위치에 배치됨.

## [2026-08] squeekboard D-Bus `SetVisible(false)` — 자동 모드로 복귀 불가한 일방향 오버라이드
- 상황: 앱에 "키보드 숨기기" 버튼을 만들어 squeekboard(라파 OS 가상 키보드)를 D-Bus로 숨겼더니,
  이후 다른 입력창에 포커스를 줘도 키보드가 다시는 안 뜸.
- 원인: `gdbus/dbus-send`로 `sm.puri.OSK0` 인터페이스를 introspect한 결과, `Visible` 프로퍼티는
  **읽기 전용**이고 `SetVisible(bool)` 메서드만 있음 — "자동(포커스 트리거) 모드로 되돌리기"에
  해당하는 API가 아예 없음. 즉 `SetVisible(false)`를 한 번이라도 부르면 그 뒤로는 수동 오버라이드
  상태로 고정됨.
- 해결: 자동 표시에 기대지 않고, **모든 TextField의 포커스 변화(`onActiveFocusChanged`)마다
  `SetVisible(true)`/`SetVisible(false)`를 대칭으로 직접 호출**하도록 앱을 설계. 즉 "자동 모드를
  쓰다가 필요할 때만 개입"이 아니라 "처음부터 끝까지 앱이 수동으로 완전히 제어"하는 쪽으로
  전환. 이미 한 번 오버라이드가 걸려 stuck된 상태라면 squeekboard 프로세스 자체를 재시작
  (`pkill -x squeekboard` 후 재기동)하면 초기화됨.
- 결과: 포커스 얻을 때 뜨고, 빈 곳 탭하면 확실히 내려감 — 실기 확인. **교훈: 플랫폼이 제공하는
  D-Bus "설정" API가 겉보기엔 단순 토글 같아도, 그게 "일회성 강제"인지 "상태 변경"인지
  introspect(`org.freedesktop.DBus.Introspectable.Introspect`)로 반드시 확인할 것.**

## [2026-08] RTSP 영상이 앱 첫 실행 시 자동으로 안 뜨고 설정 재저장해야만 나옴

## [2026-08] 라파 OS 키보드(squeekboard) — 안 뜸/안 사라짐/뒤 위젯 오터치 3연속

## [2026-08] 정지 래치 상태 불일치 — 대시보드로 아무리 조작해도 모터가 안 돎
- 상황: 라파 대시보드 터치 → `/silorobot/drive_command` 토픽에 값까지 정상 도달하는 게 확인됐는데
  (`linear.x: 5.0`), 모터는 전혀 안 돌았다. STM32 브릿지도 정상 연결, 배선도 정상.
- 원인: **나노 브릿지와 STM32의 상태 모델이 어긋나 있었다.** STM32는 `silo_controller_init`에서
  `stop_latched = true`로 부팅하는데, `stm32_uart_bridge.py`는 `_emergency_latched = False`로
  시작했다. 그래서 대시보드가 `stop_release`를 보내도
  `_on_emergency_stop`의 `elif self._emergency_latched:` 조건이 거짓이라 그냥 통과 →
  **`CMD_STOP_RELEASE(0x03)`가 단 한 번도 UART로 나가지 않았다.** STM32는 계속 잠긴 채 PWM 0.
- 시도한 것: 배선·전원·핀맵을 먼저 의심했으나 전부 정상. 토픽까지 값이 오는 걸 확인한 뒤에야
  "나노는 보내는데 STM32가 안 받는" 구간으로 좁혀졌고, 프레임 생성 로직을 읽어 원인 확정.
- 해결: 현장에서는 **대시보드 정지 버튼을 한 번 눌렀다가 해제**(True를 거치면 elif가 걸림)로 우회.

## [2026-08] `/dev/ttyACM0` Permission denied — dialout 그룹 누락
- 상황: 나노에서 `stm32_uart_bridge` 기동 시 `[Errno 13] Permission denied: '/dev/ttyACM0'`가
  무한 반복. 장치 자체는 `ls -l`로 정상 존재.
- 원인: `crw-rw---- root dialout`이라 **dialout 그룹만 접근 가능**한데 `jetson` 계정이 그 그룹에
  없었음.
- 해결: 즉시 우회는 `sudo chmod a+rw /dev/ttyACM0`(USB 재연결 시 초기화됨).
  영구 해결은 `sudo usermod -aG dialout jetson` 후 **재로그인**(그룹은 새 세션부터 적용).
- 교훈: 시리얼 장치가 "있는데 못 여는" 경우는 거의 항상 그룹 권한이다. 새 기기에 시리얼을 처음
  물릴 때 `usermod -aG dialout`을 선행 작업으로 넣어둘 것.

## [2026-08] 나노↔라파 랜선 직결 설정 — DHCP 대기·SSH 점프·키 부재 3연타
- 상황: 학교에 인터넷이 없어 나노 B01↔라파를 랜선으로 직결(고정 IP 192.168.50.20/.10)하려 했으나
