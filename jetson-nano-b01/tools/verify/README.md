# 오프로봇 검증 (tools/verify)

로봇·ROS 없이, **실제로 배포되는 코드 그대로** 자율주행 전체 사슬을 돌려보는 시험대다.
C 컴파일러와 Python 3만 있으면 노트북에서 몇 초 만에 끝난다.

```bash
python3 tools/verify/run.py
```

STM32 저장소가 옆 디렉터리(`../stm32-controller`)에 없으면 `--stm32 <경로>`로 지정한다.

## 왜 만들었나

2026-08-21 실기에서 "제자리에서 계속 돌기만 하고 진행률 0%"를 하루 종일 못 잡았다. 코드를
눈으로 읽어 부호를 판정하다 **두 번 틀렸고**, 그중 한 번은 고치려던 수정이 오히려 회전을
0으로 붕괴시켰다. 부호 하나가 뒤집히면 증상이 겉으로는 똑같아 보이기 때문에, 실기에서
알아내려면 매번 몇 시간이 든다.

그래서 **판정을 눈이 아니라 실행으로** 옮겼다. 부호를 일부러 되돌리면 시험이 실패하는지도
같이 확인한다(역검증) — 통과만 하고 아무것도 못 잡는 시험을 방지하기 위해서다.

## 무엇을 검사하나

재구현이 아니라 **원본 파일을 그대로 import 해서** 돌린다:

- `coverage_planner` / `odometry_node` / `path_follower` / `stm32_uart_bridge` /
  `safety_supervisor` — `src/silorobot_nano/silorobot_nano/`의 실제 소스
- 아케이드 믹싱·데드존·프레임 파서 — `stm32-controller`의 실제 C를 공유 라이브러리로
  컴파일해 `ctypes`로 직접 호출
- 파라미터 — `config/bootstrap.yaml`의 실제 배포 값

모델링하는 건 로봇의 물리(궤도 속도 → 이동/회전)와 **엔코더 부호 규약** 둘뿐이다. 이 둘은
실물 세계에 있는 값이라 코드에서 알아낼 수 없다.

| 절 | 내용 |
|---|---|
| 1 | 계획 생성 — 영역·안전여백 준수, 세로/가로 후보 중 짧은 쪽 채택 |
| 2 | STM32 실제 믹싱 — 전진/좌회전/우회전/정지 시 좌우 출력 부호 |
| 3 | 오도메트리 부호 — 전진 시 x 증가, 제자리 회전 시 이동 0, 추정 theta == 실제 theta |
| 4 | 계획↔오도메트리 좌표계 anchor 및 역변환 왕복 |
| 5 | **전체 폐루프** — 계획 → 추종 → 펌웨어 → 물리 → 엔코더 → 오도메트리 → 완주 |
| 6 | **역검증** — 부호를 되돌리면 실패하는가 (시험대 자체의 신뢰성) |
| 7 | 시작 자세가 ±150도까지 어긋나도 스스로 정렬해 완주하는가 |
| 8 | 대형 계획(48 웨이포인트)도 완주하는가 |
| 9~10 | 나노↔STM32 통신 — 양쪽 실제 코드로 프레임 왕복, 잡음·분할·체크섬·범위 방어 |
| 11 | 안전장치 — 부팅 래치, 안정화 대기, 미보정 시 해제 거부 |

## 한계 — 이걸 통과해도 실기는 해야 한다

시험대가 검증하지 **못하는** 것:

- **엔코더 부호 규약 자체.** 시험대는 `COUNT_DIR_L/R = -1`(전진 시 카운트 감소)을 전제로
  깔고 있고, 이건 2026-08-21 실측 캡처에서 얻은 값이다. 배선을 바꾸면 이 전제가 깨진다 —
  그때는 실기에서 `ros2 run silorobot_nano verify_signs`로 다시 확인할 것.
- 모터 실제 데드존·최대속도, 궤도 슬립, 자력 부착 상태, 벽면에서의 거동
- IMU z축이 로봇 요축과 정렬돼 있는지 (현재 `encoder_alpha: 1.0`이라 미사용)
- 거리센서 LUT (실측 전)

즉 **"코드 논리와 부호는 맞다"까지만 보장**한다. 물리값은 여전히 실기에서 재야 한다.
